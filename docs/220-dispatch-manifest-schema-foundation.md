# Dispatch Manifest Schema Foundation

Task 220 drafts the first Logistics dispatch/manifest database foundation for EveryBatch.

This is schema, permission and RLS foundation only. It does not apply the migration, run Supabase CLI, build task 221 UI, generate carrier files, connect Detrack/Cold Xpress/DK/Meal Cart, import Shopify orders, create fake operational data, allocate inventory lots, create stock movements, change QA holds, change Production, change Support, change domains or add packages.

Correct domains remain:

- `app.everybatchmrp.com`
- `admin.everybatchmrp.com`
- `cleaneats.everybatchmrp.com`
- `support.everybatchmrp.com`

Do not use `admin.everybatchmrp.com.au`.

## Migration

Drafted migration:

- `supabase/migrations/042_dispatch_manifest_schema_foundation.sql`

The migration must be manually reviewed before applying to Supabase.

## Tables Added

The migration creates nine tenant-owned Logistics tables:

- `public.logistics_carriers`
- `public.logistics_carrier_services`
- `public.logistics_dispatch_runs`
- `public.logistics_dispatch_deliveries`
- `public.logistics_dispatch_lines`
- `public.logistics_manifests`
- `public.logistics_manifest_deliveries`
- `public.logistics_manifest_lines`
- `public.logistics_carrier_exports`

Every table includes `organisation_id`. Cross-module references use tenant-safe composite foreign keys where a referenced table has tenant ownership, including carrier/service relationships, dispatch run/delivery/line relationships, manifest snapshot relationships and optional `internal_items` references.

Delivery issue operational tables are deliberately deferred. Delivery zone tables are also deferred.

## Source Of Truth Boundaries

Logistics owns dispatch runs, delivery/stop snapshots, dispatch line snapshots, manifests, manifest snapshot rows and carrier export history.

Logistics does not own finished-product master data, inventory lots, stock movements, Stock On Hand, production batches, QA holds/releases, customer/account master records, support tickets, audit logs or reporting aggregates.

The schema keeps customer/order fields as snapshots and source references only. It does not invent CRM or order foreign keys before those tables exist.

## Numbering Decision

`run_number` and `manifest_number` are nullable/manual for now. The migration comments state that authoritative numbering should be generated by a future server-side workflow.

This avoids browser-side `max() + 1` numbering and leaves atomic numbering for task 221 or a later controlled RPC if required.

## Role Mapping

`platform_admin`, `organisation_admin` and `operations_manager` receive all new task 220 Logistics permissions.

`warehouse_manager` receives dispatch run view/create/manage, manifest view/create/manage, carrier export view/create, logistics configuration view and delivery issue view/create. It does not receive carrier export manage, logistics configuration manage or delivery issue manage.

`wholesale_manager` receives dispatch run view/create, manifest view/create, carrier export view and delivery issue view/create.

`production_manager` receives dispatch run view and manifest view only.

`qa_manager` receives dispatch run view, manifest view and delivery issue view only.

`viewer` receives read-only permissions: dispatch run view, manifest view, carrier export view, logistics configuration view and delivery issue view.

`staff`, `tablet_user` and `phase_1_demo_user` receive no new task 220 Logistics permissions.

## RLS Model

RLS is enabled on every new Logistics table.

Policies follow the existing helper pattern:

- `public.is_platform_admin()`
- `public.is_active_member(organisation_id)`
- `public.has_permission(organisation_id, '<permission>')`
- `public.current_profile_id()` for actor checks where actor fields exist

Policy shape:

- Carrier and carrier service SELECT requires `logistics_configuration.view`.
- Carrier and carrier service INSERT/UPDATE requires `logistics_configuration.manage`.
- Dispatch run, delivery and line SELECT requires `dispatch_runs.view`.
- Dispatch run INSERT requires `dispatch_runs.create` and can create active draft rows only.
- Dispatch run UPDATE requires `dispatch_runs.manage` and is limited to active draft-to-draft edits. Ready, dispatched, completed and cancelled transitions are withheld for task 221 controlled functions.
- Dispatch delivery/line INSERT requires `dispatch_runs.create`; UPDATE requires `dispatch_runs.manage`; both are permitted only while the delivery and parent run remain active drafts.
- Manifest and manifest snapshot SELECT requires `manifests.view`.
- Manifest INSERT requires `manifests.create` and can create active drafts only, with no generated actor/timestamp.
- Manifest UPDATE requires `manifests.manage` and is limited to active draft-to-draft edits.
- Manifest delivery/line snapshots have no direct authenticated INSERT, UPDATE or DELETE policies. Snapshot creation is withheld until task 221 provides an atomic controlled generation function.
- Carrier export SELECT requires `carrier_exports.view`.
- Carrier export INSERT requires `carrier_exports.create` and can create pending rows only, without generated, file, error or archive metadata.
- Carrier export UPDATE requires `carrier_exports.manage` and is limited to pending-to-pending edits with the same restrictions.

No anon policies are created. No DELETE policies are created. No broad authenticated-only policies are created.

Platform admins use the same draft/pending direct-write boundaries. Platform access does not bypass immutable-history triggers or permit direct generated manifest/export creation.

## Direct Write Boundaries

Ordinary authenticated table calls may:

- create and edit active draft dispatch runs;
- create and edit active draft deliveries and lines while their parent dispatch run remains an active draft;
- create and edit active draft manifest headers without generated metadata;
- create and edit pending carrier export requests without generated/file/error metadata;
- manage carrier and carrier-service configuration while immutable identity and parent fields remain fixed.

Ordinary authenticated table calls cannot:

- transition dispatch runs out of draft;
- move deliveries between dispatch runs or lines between deliveries;
- create or mutate manifest snapshots;
- mark manifests generated, cancelled or superseded;
- create generated/failed export history or transition pending exports to outcome states;
- rewrite generated, failed, superseded or cancelled history;
- change tenant, record identity, creation identity, fixed parent or version fields.

Delivery and line write triggers lock and validate the parent draft records at the database boundary, preventing writes racing with a dispatch-run lifecycle transition.

## History Protection

Generated manifest and carrier export history is protected by trigger helpers:

- direct authenticated snapshot insertion is withheld;
- direct manifest creation/update is draft-only and cannot set generated actor/time;
- generated manifests cannot be silently rewritten;
- generated manifests may only be marked superseded without changing snapshot content;
- immutable manifest delivery and line snapshot rows cannot be updated or deleted;
- direct carrier-export creation/update is pending-only and cannot set generated/file/error metadata;
- generated/failed carrier export records cannot be silently rewritten;
- carrier exports should be re-created as new versioned records instead of overwritten.

The trigger functions use fixed `search_path = public`, do not use dynamic SQL and do not use `SECURITY DEFINER`.

Actor-validation triggers cover every actor column in the migration. Non-null actors must be active members of the record organisation. A platform admin operating without tenant membership may use only their own current profile as the actor, preventing arbitrary cross-tenant profile attribution. Historical actor references are not revalidated when an unrelated field changes.

Immutable-field triggers protect `id`, `organisation_id`, `created_at`, `created_by_profile_id` where present, and historical parent/version identity. Carrier services cannot move between carriers; deliveries cannot move between runs; lines cannot move between deliveries; manifest/export parent and version identity cannot be rewritten.

## Task 221 Controlled Boundaries

Task 221 should introduce reviewed `SECURITY DEFINER` lifecycle functions rather than reopening direct table policies. The manifest-generation transaction is expected to:

1. derive and validate the authenticated actor and tenant membership;
2. lock the draft dispatch run and manifest inputs;
3. validate all delivery data;
4. assign authoritative manifest numbering/versioning;
5. insert the manifest delivery and line snapshots;
6. mark the manifest generated;
7. commit all changes atomically.

Controlled functions should also own dispatch-run lifecycle transitions and any future carrier-export outcome transitions. Export generation/re-export remains a later reviewed workflow; re-export must create a new version rather than rewrite an existing result.

- confirm generated history trigger behaviour is acceptable for the first manifest workflow.

## Rollback Notes

Because this migration creates a new foundation, rollback before production use would mean dropping the new Logistics RLS policies, triggers, functions, tables and newly seeded granular permissions/role mappings. Once operational dispatch data exists, rollback should be treated as data-retention work, not a casual drop.
