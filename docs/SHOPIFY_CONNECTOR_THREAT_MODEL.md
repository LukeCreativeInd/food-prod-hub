# Shopify Connector Threat Model

## Purpose And Scope

This Task 229 model describes threats to a future public EveryBatch Shopify app, its minimal embedded merchant surface, connector ingress, credentials, Commerce records and manufacturing relationship. It is a design input for Tasks 232 and 233. No control listed here was implemented during Task 229.

Likelihood and impact are planning classifications, not measured production risk. Implementation must use current official Shopify libraries and documentation, and must be independently security-reviewed before App Store submission.

## Trust Boundaries

1. Shopify merchant browser and Shopify Admin to EveryBatch embedded surface.
2. Shopify installation/token service to EveryBatch callback or token-exchange handler.
3. Shopify webhook delivery service to EveryBatch ingress.
4. EveryBatch public ingress to durable integration processing.
5. Connector worker to Shopify GraphQL Admin API.
6. Credential service to encrypted token storage and encryption key provider.
7. Shopify store/connection to EveryBatch manufacturing organisation and facility.
8. EveryBatch tenant users, Platform Admin and Support to restricted diagnostics.
9. Development, staging, preview and production environments.

## Control Invariants

- No organisation, facility, connection or manufacturer identity is trusted from browser, callback, webhook or job payload without server-side resolution.
- Shopify authentication, Shopify store-owner authorisation, EveryBatch user authentication and manufacturer acceptance remain separate controls.
- Credentials are encrypted, non-tenant-readable and absent from Support/Platform Admin views and logs.
- A verified webhook is not sufficient evidence of current state; idempotency, temporal selection and reconciliation remain mandatory.
- Source evidence can import before mappings are complete, but actionable demand cannot.
- No source event creates Inventory stock movement, QA state or Production execution by itself.
- Preview/local/staging and production registrations, secrets, stores and callback hosts remain isolated.

## Incident Response Direction

1. Contain: disable the affected app environment, connection, credential version, webhook route or worker category without deleting evidence.
2. Preserve: retain redacted event IDs, digests, processing attempts, configuration versions and affected internal IDs; never copy tokens or raw protected payloads into tickets.
3. Rotate/revoke: rotate app or encryption credentials, revoke/reinstall shop access where required and invalidate pending install state.
4. Assess: identify stores, tenants, data categories, time window and source-to-demand effects; involve legal/privacy professionals for notification and deletion duties.
5. Recover: reauthorize, restore reviewed configuration, run bounded reconciliation and verify demand parity before re-enabling actionable intake.
6. Learn: record a business audit event and security incident review, update tests/runbooks and validate Shopify configuration.

## Implementation Status

Task 229 implemented no controls. Task 233 now implements the local control foundation: strict shop/domain/GID checks, official token/HMAC validation, environment/host isolation through routes, credentials, installations, jobs and environment-scoped worker claim/completion RPCs, encrypted offline credentials, no tenant credential access, one-time claims, narrow trusted RPCs, payload/topic limits, event-ID idempotency, reference-only jobs, stale-projection guards, redacted logs and durable retries. Migration 047 is live/registered, but its PostgreSQL domain-regex escaping requires unapplied Migration 048 before the strict-domain control is operationally accepted. No app/store has been validated, so production scheduler, monitoring, incident response, key operations and App Review evidence remain open controls.
